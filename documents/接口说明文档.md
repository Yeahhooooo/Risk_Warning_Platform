### 1.2 统一响应结构

除 knowledge、bert 两个服务外（它们直接返回 `Map`），其余接口统一返回：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

| 字段 | 类型 | 是否为空 | 说明 |
| --- | --- | --- | --- |
| code | Integer | 否 | 200 表示成功；其他值表示失败 |
| message | String | 否 | 成功固定为 `success`，失败为错误描述 |
| data | T | 可 | 业务数据，失败时为 `null` |

**重要**：`GlobalExceptionHandler` 返回的也是 `Result` 对象且**未设置 HTTP 状态码**，所以业务失败时 HTTP 状态码**仍然是 200**。判断成败必须看 `code` 字段，不能只看 HTTP 状态。

各类异常对应的 `code` / `message`：

| 触发场景 | code | message |
| --- | --- | --- |
| 成功 | 200 | `success` |
| `BusinessException` | 异常自带 code | 异常自带描述 |
| 未捕获的系统异常 | 500 | `系统异常，请稍后重试` |
| `IllegalArgumentException`（参数/找不到记录） | 500 | `参数异常: {原因}` |
| Bean Validation 校验失败 | 500 | `参数校验异常: {字段}: {提示}; ...` |
| 请求体缺失或 JSON 格式错误 | 500 | `请求体缺失或格式错误` |
| 路径不存在 | 500 | `无效的请求路径: {URL}` |

### 1.3 认证机制

需要登录的接口由方法上的 `@AuthRequired` 注解标记，由 `AuthAspect` 切面拦截：

1. 从请求头 `Authorization` 读取令牌，格式为 `Bearer {token}`（也兼容不带前缀的裸 token）。
2. 用 `JwtUtils` 解析：算法 HS256，密钥硬编码在 `JwtUtils.SECRET_KEY`，Claims 含 `userId`、`email`、`fullName`，有效期 **24 小时**。
3. 解析成功后将 `User` 实体放入 `UserContext`（ThreadLocal），方法执行结束后自动清理。

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

**认证失败的表现**：切面抛出 `RuntimeException`，被全局异常处理器捕获，最终返回 `{"code":500,"message":"系统异常，请稍后重试"}`（HTTP 200）。这**不是**标准的 401，前端不要依赖 HTTP 状态码判断登录态。

下表中标记「认证：是」的接口即需要该请求头。

### 1.4 参数位置约定

| 位置 | 含义 | 示例 |
| --- | --- | --- |
| Path | 路径变量，写在 URL 路径里 | `/user/{userId}` 中的 `userId` |
| Query | URL 查询参数 | `/user/email?email=a@b.com` |
| Header | 请求头 | `Authorization` |
| Body | 请求体，`Content-Type: application/json` | 注册、登录等 |
| Form | 表单字段，`Content-Type: multipart/form-data` | 文件分片上传 |

### 1.5 状态标记说明

| 标记 | 含义 |
| --- | --- |
| ✅ | 按参数正常查询数据库/ES 并返回真实数据 |
| 🔒 | **演示期固定返回**：请求参数被完全忽略，恒定返回《JUDGE-A4DF00BA94F3 合规判定报告》写死的结果 |
| ⚠️ | 未实现或占位接口，调用不会得到有效业务数据 |

### 3.1 用户管理（UserController）

基础路径：`/user`

#### 3.1.1 用户注册 ✅

| 项 | 内容 |
| --- | --- |
| 路径 | `POST /user/register` |
| 网关路径 | `POST /api/org/user/register` |
| 认证 | 否 |
| Content-Type | `application/json` |

**请求参数（Body）**

| 参数名 | 类型 | 必填 | 说明 | 校验规则 |
| --- | --- | --- | --- | --- |
| email | String | 是 | 登录账号，用户邮箱，全局唯一 | `@NotBlank`、`@Email` |
| password | String | 是 | 登录密码 | `@NotBlank`、`@Size(6-20)` |
| fullName | String | 是 | 用户姓名 | `@NotBlank`、`@Size(max=50)` |

**请求示例**

```json
{
  "email": "newuser@example.com",
  "password": "Password123",
  "fullName": "张三"
}
```

**响应字段（`data` 为 UserResponse）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| data.id | Long | 用户 ID |
| data.email | String | 用户邮箱 |
| data.fullName | String | 用户姓名 |
| data.avatarUrl | String | 头像 URL，可为空 |
| data.createdAt | String | 创建时间 |
| data.updatedAt | String | 更新时间 |

**响应示例**

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "id": 1,
    "email": "newuser@example.com",
    "fullName": "张三",
    "avatarUrl": null,
    "createdAt": "2026-09-20T10:00:00",
    "updatedAt": "2026-09-20T10:00:00"
  }
}
```

**失败响应**（邮箱重复等，注意 HTTP 仍为 200）

```json
{ "code": 500, "message": "邮箱已被注册", "data": null }
```

### 4.0 演示期固定返回（三个接口共同行为）🔒

`general`、`indicatorResult`、`risk` 三个接口当前处于**演示阶段**，行为如下：

- **完全忽略请求参数**：`assessmentId` 传什么都不参与取数——真实评估记录 id、库中不存在的 id（1 / 123 / 999999）、甚至不传，控制器都直接返回 `FixedAssessmentData.assessment()`。控制器已不再持有评估仓储，**不查数据库、不查 ES**，响应体与传参完全无关。
- **身份字段同样固定**：返回体里的 `assessmentId` / `projectId` 恒为 `900001`、评估时间恒为 `2026-09-19 19:46:40`。即 org 模拟评估流程刚生成的记录（如 id 425 / project 349）也不会再作为返回体里的 id 出现（此前口径是「内容固定 + 身份按 id 回查」，现已改为完全无条件）。
- **服务层仍保留模拟评估识别**：`ReportServiceImpl.isSimulated` 会识别 `details` 内带固定数据集标记的落库记录（解析 `assessmentDetailVO.assessmentId / projectId` 是否为 `900001`，**不看文本是否相等**），供内部调用（如 `AssessmentServiceImpl` 的真实评估回写路径）使用；HTTP 三个接口现在不会走到这条分支。
- **待评估记录**：评估记录尚未完成（`details` 为空）时不属于模拟评估；由于接口已不按 id 取数，这类记录同样返回固定数据。
- **数据源**：《JUDGE-A4DF00BA94F3 合规判定报告》+《课题三任务三对山东XX国际贸易公司的判定结果的风险指标追溯对应文档》，覆盖 6 大风险维度、12 个风险点，每个风险点对应一条完整的知识库指标路径（维度 &gt; 二级指标 &gt; 三级指标 &gt; 三级指标项），指标名为路径最后一级。
- **完整路径的回传字段 `relatedIndicator`**：`risk` 接口的**每个风险点**、`indicatorResult` 的**每条指标**都会带上 `relatedIndicator`（即上面那条完整路径）；org 侧 `details` 里的 `indicatorDistributionVO.indicatorScores[].relatedIndicator` 是同名字段。12 条路径全量见 [9.11](#911-固定数据集的-12-条完整指标路径)。真实评估没有该元数据，字段为 `null`。
- **指标得分保留两位小数**：12 条指标得分都是按多条行为加权后的结果（如 `30.25`、`16.42`、`12.56`），不再使用整数档位；`risk` / `indicatorResult` / org `details` 三处口径完全一致。
- **不返回「相关法规」**：判定报告只在产品标识与劳动用工两类风险点上给出法律依据，为保持 12 条口径一致，`relatedIndicators[].relatedBehaviors[].relatedRegulations` 一律输出**空数组 `[]`**（真实评估写入的才是规则库命中的法条）。
- **风险点与行为逐条对齐**：12 个风险点共对应 **21 条行为证据**，全部按判定报告原文逐条列出，不再把多条事实揉成一句 `①②③`。一个风险点可对应 1～5 条行为；同一条事实也可以同时挂在多个风险点下（例如「未办理两用物项出口许可证」同时命中出口管制物项合规性与进出口许可证合规性），这类跨风险点的相同描述是刻意保留的。全量对应关系见 [9.12](#912-固定数据集的-12-个风险点与行为证据对应关系)。

### 4.4 ⚠️ org 的 `details` 与 report 响应存在字段差异

这一点经实测确认，前端接入时必须注意。

`org` 接口 `data.details` 里的 JSON 字符串由 **fastjson2** 生成，而 report 三个接口的 HTTP 响应由 **Jackson** 序列化。两个库对「枚举作 Map key」的处理规则不同，同一份数据因此出现两种 key：

| 位置 | 序列化库 | `dimensionRiskDistribution` / `dimensionDistributions` 的 key | `riskDimensionEnum` 字段值 |
| --- | --- | --- | --- |
| report 接口响应 | Jackson | **中文展示名**，如 `企业关联方风险` | 中文展示名 |
| org `data.details` 字符串 | fastjson2 | **英文枚举名**，如 `ENTERPRISE_RELATED_RISK` | 英文枚举名 |

其余差异：

| 项目 | report 响应（Jackson） | org details（fastjson2） |
| --- | --- | --- |
| 时间格式 | `2026-09-19T19:46:40`（ISO，T 分隔） | `2026-09-19 19:46:40`（空格分隔） |
| `null` 字段 | 保留并输出 `null` | 直接省略该字段 |

**接入建议**：前端对维度 key 做一层归一化（中文名与枚举名互相兼容），或**统一只从 report 接口取详情**，`org` 接口仅用于获取 `assessmentId`、`overallScore`、`overallRiskLevel` 等主记录字段。

> 如需彻底消除该差异，可把 details 快照的生成方式由 fastjson2 改为 Jackson（或反过来统一），但这会同时影响 org 侧的既有输出，需同步回归验证。

## 八、notification 服务（WebSocket）

通知服务不提供 REST 接口，仅提供 WebSocket 长连接通道，用于向前端推送评估进度与风险提醒。

### 8.1 连接地址

| 场景 | 地址 |
| --- | --- |
| 直连 | `ws://localhost:9090/ws` |
| 经网关 | `ws://localhost:8088/api/notification/ws` |

- 端口来自网关默认值 `NOTIFICATION_WEBSOCKET_URI`（`ws://localhost:9090`），可用环境变量覆盖。
- 服务使用 Netty 实现（非 Spring WebSocket），HTTP 端口 8091 不承载 WebSocket。
- 服务端支持标准的 Ping/Pong 帧（收到 `PingWebSocketFrame` 自动回 `PongWebSocketFrame`）。

### 8.2 客户端 → 服务端消息

| type | 其他字段 | 说明 |
| --- | --- | --- |
| `bind` | `userId`（Long，必填） | 绑定用户 ID，绑定后该连接才会收到对应用户的推送 |
| `ping` | — | 心跳，服务端回 `{"type":"pong"}` |
| 其他 | — | 服务端回显：`{"type":"received","message":"<原文>"}` |

**绑定请求示例**

```json
{ "type": "bind", "userId": 1 }
```

### 8.3 服务端 → 客户端消息

| type | 字段 | 说明 |
| --- | --- | --- |
| `bind_success` | `userId`、`message` | 绑定成功，`message` 为 `用户绑定成功` |
| `bind_error` | `userId`（null）、`message` | 绑定失败，`message` 为 `用户ID不能为空` |
| `pong` | — | 心跳响应 |
| `received` | `message` | 其他消息回显 |
| `error` | `message` | 消息格式错误，`message` 为 `消息格式错误` |

**绑定成功响应示例**

```json
{ "type": "bind_success", "userId": 1, "message": "用户绑定成功" }
```

> 连接建立/断开由 `WebSocketChannelManager` 统一维护，未绑定 `userId` 的连接不会收到业务推送。
