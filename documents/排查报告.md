## 共享远程 Redis 的队列隔离

已观察到两个不同来源的客户端同时 RPOP 原来的 JDK 序列化队列键 `file:confirmed:queue`。
这会竞争消费；任务被另一开发环境取走后，本机不会出现 RECEIVED 日志。
org 的 `application.yml` 现在将 `org.upload.queue-key` 默认设为 `file:confirmed:queue:lenovo`。
上传确认和后台消费共用 UploadTaskQueue，确保两端使用同一个配置。
其他开发者设置自己的 `UPLOAD_CONFIRM_QUEUE_KEY`；同一正式部署内协作的实例则应使用同一个值。
启动时检查 `status=CONFIGURED` 和 `status=START` 的 queueKey 是否是预期值；Nacos 或启动参数可能覆盖本地配置。
旧队列中的任务不会迁移，也不会自动重新执行已经被取走的旧任务。
Redis 键仍使用项目原有序列化器；redis-cli 查询普通文本键不一定等于查询 Java 实际使用的键。
在各服务控制台搜索 `[AssessmentFlow]`，再用 `projectId=实际项目ID` 筛选；创建评估记录后可进一步使用 assessmentId。
本次没有新增日志文件配置，日志输出沿用现有控制台/文件设置。INFO 级别需要开启。

## 文件上传入口的阶段顺序

| 服务 | stage | 含义 |
| --- | --- | --- |
| org | UPLOAD_CONFIRM | 收到确认上传请求；RETURNED 只表示方法返回 |
| org | UPLOAD_QUEUE_ENQUEUE | QUEUED 表示 Redis 入队成功；FAILED 表示写入失败 |
| org | UPLOAD_QUEUE | 后台从配置的 queueKey 取出任务 |
| org | FILE_MERGE | 合并分片并保存文件记录 |
| org | ASSESSMENT_CREATE | COMMITTED 表示评估记录事务已提交 |

| processing | BEHAVIOR_TASK | 收到文件处理消息 |
| processing | DOCUMENT_EXTRACT | 文档提取为内部文本文件 |
| processing | BEHAVIOR_BATCH | Spring Batch 开始/结束，完成时记录 jobExecutionId |
| processing | BERT_CLASSIFY | 批量分类；step 区分并行分区 |
| processing | KNOWLEDGE_VECTORIZE | 批量向量化 |
| processing | ES_BEHAVIOR_WRITE | 行为写入 ES |
| processing | KAFKA_SEND | topic=indicator_calculation_tasks |
| processing | INDICATOR_TASK | 收到指标计算消息 |
| processing | INDICATOR_CALCULATE | 指标计算，记录 attempt 和耗时 |
| processing | ES_BEHAVIOR_READ | 读取项目行为，记录 behaviorCount |
| processing | INDICATOR_SAVE | 保存指标结果 |
| processing | KAFKA_SEND | topic=assessment_completed_events |
| report | REPORT_AGGREGATE | 汇总风险、总分和报告 |

直接调用 process-project 接口时，从 DIRECT_ASSESSMENT 开始，跳过文件上传链路；其内部仍有 ES_BEHAVIOR_READ、INDICATOR_SAVE 和完成事件日志。

## 如何判断

- FAILED：查看该行下方的异常堆栈，并检查重试是否最终成功。
- DEGRADED：现有逻辑允许继续，但分类/向量化结果不完整，可能影响下游计算。
- FINISHED：该调用阶段结束，不保证结果完整；同时检查 DEGRADED。DONE 是相应阶段完成，不表示整条评估链路完成。
- START 长时间没有结束：该调用可能阻塞，结合 elapsedMs、线程名、step 和 attempt 判断；并行日志会交错。
- KAFKA_SEND START 不等于发送成功，只有 ACK 表示 broker 确认；partition/offset 可以定位消息。ACK 不等于下游已消费。
- UPLOAD_QUEUE_ENQUEUE QUEUED 后没有 UPLOAD_QUEUE RECEIVED：检查 org 后台队列消费和 Redis。
- UPLOAD_QUEUE_ENQUEUE FAILED：Redis 写入失败；现在确认接口会返回失败，避免误报成功。
- 有 broker ACK 但没有下游 RECEIVED/START：检查消费者、消费组、topic 和积压。
- ES_BEHAVIOR_READ 的 behaviorCount=0：检查同项目的文档提取和行为入库日志。
- REPORT_AGGREGATE DONE 后页面不更新：检查前端结果查询和通知；processing 设置 ASSESSED 不代表 report 已完成汇总。

示例：`[AssessmentFlow] stage=KNOWLEDGE_VECTORIZE status=DEGRADED projectId=123 step=workerStep:partition0 reason=exception_continuing_without_vectors`
表示该分区向量化异常，现有逻辑继续写入行为，并非成功生成向量。

排查时保留同一 projectId/assessmentId 从请求到失败的日志及异常堆栈。不要只截取 Kafka 初始化日志。

## report 报 No indicator results（评估 339）

项目 257 的两条行为在 ES 中均有 768 维向量，但默认查询的 `_source` 没有返回向量。
旧实现用 null 构造 kNN 查询，捕获异常后返回空候选，随后把空保存标记为完成并发送完成事件。
修复后行为、指标、法规查询都显式包含 `*` 和对应向量字段；保留所有普通字段供原有计算使用。
候选检索失败会带完整堆栈向上传播，空指标结果不能通过保存阶段，也不能发布完成事件。

生效需要重启 processing。已有失败评估不会因为重启 report 自动修复。
对于已经完成行为入库的项目，可在 processing 更新后通过现有接口重新计算：
`POST /api/processing/api/behavior/process-project/257/339`（网关路径，需正常用户认证）。
该接口会写入评估结果并发送完成事件，不能当作只读检查；重算前确认使用正确项目和评估ID。

`BehaviorProcessingVectorTest` 是不联网的回归测试。
`BehaviorProcessingLiveReadTest` 默认禁用，仅显式设置 `assessment.live.es=true`、
`assessment.live.nacosBase` 和可选 `assessment.live.projectId` 时运行；只读取 ES 并计算映射，不更新数据库、不发 Kafka。
