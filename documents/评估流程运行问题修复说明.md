# 评估流程运行问题修复说明

整理日期：2026-10-09。本文依据当前项目代码、Git 提交记录、已有排查报告及本地测试产物，说明此前评估流程无法顺利完成的原因、修复措施和运行注意事项。

## 1. 问题背景与正常流程

用户上传文件并确认后，系统通过多个服务异步完成评估：

```text
确认上传 → Redis 上传队列 → org 合并文件、创建评估
    → behavior_processing_tasks
    → processing 提取文本、分类、向量化、行为写入 ES
    → indicator_calculation_tasks
    → processing 检索指标与法规、计算并保存指标结果
    → assessment_completed_events
    → report 汇总风险、分数与报告
    → notification_tasks → notification → WebSocket → 页面更新
```

此前“跑不通”并非单一接口错误：任务可能在队列中被其他环境取走，也可能在向量检索或异步执行阶段失败，或已经完成报告但通知没有到达浏览器。确认上传成功、Kafka 发送成功和评估完成分别代表不同阶段，不能相互替代。

## 2. 主要故障与修复

### 2.1 共享 Redis 队列导致任务被其他环境消费

**现象：** 确认上传后入队成功，但本机 org 没有后续消费日志。

**原因：** 历史排查观察到两个不同来源的客户端同时消费原来的 `file:confirmed:queue`。Redis 出队具有竞争性，任务被其他环境取走后，本机自然无法继续执行。

**修复：** 使用 `UploadTaskQueue` 统一上传确认端和后台消费端的队列配置，并通过 `UPLOAD_CONFIRM_QUEUE_KEY` 隔离不同开发环境。入队失败向调用方返回失败，避免页面误认为任务已提交。

**当前配置：** `risk-warning-org/src/main/resources/application.yml` 中默认值为 `file:confirmed:queue:dcw`；早期排查文档中的 `:lenovo` 是当时配置。部署时以实际生效的配置为准，尤其检查 Nacos、环境变量和启动参数的覆盖情况。不同开发者应使用不同队列；同一部署内协作的实例应共享指定队列。

旧队列任务没有自动迁移；已经被取走且未留下持久记录的历史任务不能靠重启恢复。

### 2.2 ES 未返回行为向量，导致指标结果为空

**现象：** report 报 `No indicator results`。历史案例为项目 257、评估 339：ES 中两条行为已有 768 维向量，但查询结果未返回向量字段。

**原因：** 旧实现使用缺失的向量构造 kNN 查询，检索异常被捕获并转为空候选；后续空结果仍被视为保存完成，并发布评估完成事件，最终在 report 阶段暴露问题。

**修复：** 行为、指标和法规查询显式请求普通字段及对应向量字段；候选检索异常向上抛出并保留堆栈。指标结果为空时终止处理，避免发布误导性的完成事件。

**效果：** 将故障定位提前到实际失败的计算阶段，避免下游收到缺少指标结果的完成事件。相关实现位于 `BehaviorProcessingService.java`，对应回归测试为 `BehaviorProcessingVectorTest`。

已完成行为入库的历史失败评估，需要在更新 processing 后按具体项目和评估重新计算；单独重启 report 不会补齐指标结果。

### 2.3 内存执行和消息交接缺少可靠恢复

**问题：** 异步任务如果只存在内存，进程退出后难以恢复；数据库提交与 Kafka 发送分开执行，可能出现数据库已有记录但下游没有消息的情况。输入被提前删除还会使重试失去依据。

**修复：** 引入 PostgreSQL `assessment_work` 持久任务表，形成 Redis → 持久任务 → 业务执行 → Kafka outbox → 下游 inbox 的交接机制。

| 环节 | 修复后的处理方式 | 作用 |
| --- | --- | --- |
| 上传入队 | 保存 taskId 和文件元数据快照 | 减少对临时元数据的依赖 |
| Redis 交接 | 原子移入 processing 列表，数据库成功后才确认移除 | 交接失败时保留任务 |
| 序列化兼容 | 按原始字节确认队列项，兼容旧 Java 序列化数据 | 避免确认时无法匹配原队列项 |
| 上传执行 | 文件记录、评估记录、下游消息和任务完成状态同事务提交 | 数据库失败时整体回滚 |
| 消息接收 | Kafka 监听器先持久化 inbox，再允许提交位点 | 接收失败时不静默跳过 |
| 任务去重 | 使用 namespace、任务类型和 messageId 去重 | 降低重复消息造成的重复处理 |
| 下游发送 | 业务事务写入 outbox，发送成功收到 broker ACK 后标记 DONE | 发送失败可持续重试 |
| 失败恢复 | 普通任务间隔 30 秒重试，累计三次后 FAILED，并保留错误和输入 | 可定位故障后恢复指定任务 |
| 文件合并 | 按数字顺序合并分片，重试截断旧输出，失败保留输入 | 避免分片乱序和残留输出影响重试 |

服务首次启动会初始化任务表及索引，初始化失败会阻止启动。任务 namespace 必须在重启和迁移时保持稳定，否则新实例不会领取旧 namespace 下的任务。

这套机制支持至少一次执行。ES 写入、文件操作和 Spring Batch 元数据不能随业务数据库事务统一回滚，仍需关注重试中的业务幂等性。

### 2.4 报告完成后页面仍无通知

**原因与证据：** 历史 Kafka 快照显示 report 与 notification 的消费组存在多个成员。notification 的用户连接保存在当前进程内存中，消费到消息的实例可能没有对应用户连接。另一个消费者的来源尚未定位，不能把本机无日志直接判定为消息未发送。

**已修复内容：**

- 后端修复旧连接清理误删新用户映射，以及重复绑定时关闭同一连接的问题。
- 网关将 WebSocket 路由放在通用通知 HTTP 路由前，目标可通过 `NOTIFICATION_WEBSOCKET_URI` 指定。
- 前端修复 CONNECTING 状态重复连接、重试上限未生效、旧连接事件干扰新连接，以及旧定时器未清理的问题。
- 离线通知日志明确显示 `WS_OFFLINE / NOT_STORED`，避免将尚未实现的保存能力误认为已完成。

历史前端配置使用 Vite `/ws` 代理直连 notification。验证通知时需先确认当前访问路径；网关仍有鉴权要求。Netty 写入成功也不等于浏览器已经处理通知。
